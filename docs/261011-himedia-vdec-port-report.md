## 3. What changed and why

### 3.1 Scope: what was ported and what was cut
- **Ported:** `histb-vdec-core.c`, `-mpeg4`, `-vc1`, `-mvc`, `histb-vpss.c/.h`, uapi `histb-vpss.h`, the vdec and vpss bindings, a Kconfig/Makefile limited to `VIDEO_HISTB_VDEC` and `VIDEO_HISTB_VPSS`.
- **Not ported (as asked):** `histb-dmx`, `histb-jpge`, `histb-venc*`. Nothing in vdec depends on them [tested: it links].
- **Cut: AVS/AVS+ (1,636 lines out of core, 14,597 -> 12,961).** The 6.12 tree added `V4L2_PIX_FMT_AVS_SLICE`, `V4L2_CID_STATELESS_AVS_*`, `struct v4l2_ctrl_avs_*` to `videodev2.h`, `v4l2-controls.h`, `v4l2-ctrls-core.c`, `v4l2-ctrls-defs.c`, `v4l2-ioctl.c`, `v4l2-ctrls.h` [read: `grep -rIl` over the 6.12 tree]. None exists in 6.18; adding a private uAPI to the core is out of scope and AVS was not on your codec list. AVS was also the **only** user of (a) the VDH MMU identity page table and its error pages, (b) `histb-avsp.bin`, (c) the "one CMA arena" buffer path. All of those went with it. Every other codec already ran with the VDH MMU in bypass (`histb_vdec_program_smmu(vdec, false)`), now spelled `histb_vdec_smmu_bypass()`. The SMMU *status/fault register reads* stay (they are used by the H.264/VP9/MPEG-4/VC-1 completion checks). Method: `strip_funcs.py` deleted 36 AVS/SMMU-identity functions by name, `strip_avs_sites.py` edited the remaining call sites with asserted single matches; the compiler then found nothing left over.
- **Kept:** `HISTB_VDEC_SCD_AVS_FLAG` writes of 0 at job start; they put the SCD into its non-AVS state and cost nothing [inferred].

### 3.2 6.12 -> 6.18 API fixes (compiler-found)
1. `struct platform_driver.remove_new` -> `.remove` (void return), both drivers.
2. `v4l2_fh_add(fh)` / `v4l2_fh_del(fh)` -> take the `struct file *` (`v4l2_fh_add(&ctx->fh, file)`).
3. `MODULE_IMPORT_NS(DMA_BUF)` -> `MODULE_IMPORT_NS("DMA_BUF")` (string namespace).
4. `nth_page()` no longer exists (used by my own `histb-dma.h`; `page + i` is the 6.18 idiom for a contiguous block).
5. `v4l2_m2m_buf_done_and_job_finish_states()` is a **non-upstream core function** the 6.12 tree added. Ported into `v4l2-mem2mem.c/.h` (the upstream function becomes a one-line wrapper). It is the only change to media core in 0008. **Consequence: `v4l2-mem2mem.ko` must be rebuilt and installed from the same tree as `histb-vdec.ko`**, or insmod fails with `Unknown symbol v4l2_m2m_buf_done_and_job_finish_states`.
6. AVS-only symbols (`V4L2_PIX_FMT_AVS_SLICE`, `V4L2_CID_STATELESS_AVS_*`, `V4L2_AVS_*`, `struct v4l2_ctrl_avs_*`) - see 3.1.

### 3.3 32-bit ARM fixes
1. **`histb_vdec_vp9_scale_fp()`**: `((u64)ref << 14) / current_size` -> `div_u64()`. On ARM32 the plain division emits `__aeabi_uldivmod`, which `arch/arm/lib` does not provide [read: directory listing has `div64.S`, no `uldivmod`], so the module would link as `.ko` and fail to load.
2. **`mpeg4_round_div()`**: signed 64-bit `/` -> `div_s64()` (7 call sites inlined into `mpeg4_parse_vop`, `__aeabi_ldivmod`).
3. **VC-1 BPD timeout** (`histb_vdec_...` poll loop): `HISTB_VDEC_VC1_BPD_TIMEOUT_MS * NSEC_PER_MSEC` is `4000 * 1000000L`, which overflows a 32-bit `long` to **-294,967,296** (gcc: `-Woverflow`). It is compared against a `u64` elapsed time, so the timeout could never fire and a stuck bit-plane decode would hang its worker forever. Cast to `(u64)`.
4. `-Wparentheses` in the VP9 picture message (`!!(...) | !!(...) << 1`) - parenthesised.
5. **Highmem, the important one - new `histb-dma.h`.** In 6.18 `dma_alloc_noncoherent()` is literally `page = dma_alloc_pages(); return page ? page_address(page) : NULL;` [read: `include/linux/dma-mapping.h:489`]. For a HIGHMEM page `page_address()` is NULL, so the call **fails and leaks the contiguous block it just allocated** (CMA pages are never freed). The box's `.config` has `CONFIG_HIGHMEM=y`, `VMSPLIT_3G`, 2 GB RAM and the boot log puts CMA at `0x76800000`, i.e. above the ~760 MB lowmem limit [read: .config, dts comment; the lowmem figure is inferred]. Every decoded tile/PMV surface and every cacheable capture buffer goes through that call, so **without this fix decoding would fail on the first frame** [inferred from the source; not run]. `histb_dma_alloc_noncoherent()` falls back to `vmap()` for highmem blocks; lowmem keeps the linear address. Five call sites use it (vdec: capture buffers, tile, PMV; vpss: staging). Cache maintenance is unchanged (`dma_sync_single_*` by DMA handle; the A53 D-cache is physically tagged, so the second mapping does not alias [inferred]).

### 3.4 What I checked and found already safe [read]
No `readq/writeq`, no `CONFIG_64BIT`/`BITS_PER_LONG`, `dma_set_mask_and_coherent(32)`, DMA addresses are checked with `upper_32_bits()` before they are written to 32-bit registers on most paths (I did not audit every site), `%llx` prints cast to `unsigned long long`. `dma_addr_t` is 32-bit here (no LPAE).

## 4. Clock patch 0009 (diff of theirs vs ours)

| Item | Community 6.12 | Ours (0009) |
| --- | --- | --- |
| `HISTB_VDH_CLK` / `_DSP_` / `BPD` | 65 / 66 / 67 | **57 / 58 / 59** |
| `HISTB_VPSS_CLK` | 89 | **60** |
| `HI3798CV200_VPSS_MUX` (inner) | 154 | **89** |
| `HI3798CV200_FIXED_333M` (inner) | (their numbering) | **88** (new) |
| fixed-rate `300m`, `400m` | registered | **now registered** (ids 73/74 existed as defines only) |
| gates | `0x78` bit 0, bit 1; `0x88` bit 0; `0xf0` bit 0 (parent `vpss_mux`) | same |
| mux `vpss_mux` | `0xf0`, shift 8, width 2, parents 333/400/300 | same |

Why renumber: their public ids (65..91) sit inside our inner-clock window (`HI3798CV200_INNER_CLK_OFFSET 64`, fixed/mux ids 65-87), so using them would collide with `24m`, `25m`, ... in the clock table. Ids 51-56 (SATA, SDIO1) are untouched; 57-63 were free, `HI3798CV200_CRG_NR_CLKS` is 128 so 88/89 fit. Not diffed/ported: their other additions (AIAO, TSI, DMX, VENC, VDP, HDMI, JPGE, GPU, CPU clocks) are out of scope; the AIAO ids `51/52` in their header are *their* AIAO and would collide with our SATA ids if ever ported.

**Finding: the community tree does not contain the two CABAC files** - only `firmware/hisilicon/histb-avsp.bin` and a README about it exist [read: `find`]. The driver calls `request_firmware_direct()` for both and fails the job with `failed to load hisilicon/histb-*-cabac.bin` otherwise. I rebuilt them from the vendor sources already on disk (`hisilicon-kernel-4.4.35`, CV200 `HD_FULL/32bit`), with `tools/extract_cabac.py`:
- **H.264, 5,120 B:** `g_CabacMN` (`common/syntax/h264.S`, `.size 5120`) dumped byte for byte. The vendor driver `memcpy`s the same 5,120 bytes into the same hardware table (`Write_V400R003_CabacTab`). **[read], but I cannot independently validate the contents** - the layout is hardware-packed, not (m, n) bytes.
- **HEVC, 928 B:** the vendor builds this at run time (`HEVCWriteCabacTab`) from `s_InitValue[480]` in `vdm_hal_hevc.S`: three init types, first one skips 16 leading `-1`s (144 + 160 + 160 = 464 pairs), `m = (v>>4)*5-45`, `n = ((v&15)<<3)-16`, `-1` -> (0,0), then a final pairwise byte swap. I re-implemented that by reading the ARM code, not by running it. **[inferred]; the swap direction and the 144-entry first set are the places a mistake would hide.** A wrong table yields garbage HEVC but H.264 would still work, so test H.264 first.
- Install: `install -D -m0644 histb-*-cabac.bin /lib/firmware/hisilicon/`. If the module is loaded before the rootfs is up, firmware load fails at the first stream, not at probe.

## 7. Uncertain spots

1. **TrustZone / secure access to the VDH [unknown].** The decoder registers (`0xf8c30000`) might sit behind TZPC on this firmware, in which case the first register read aborts (SError / hang) rather than failing cleanly. Evidence for "non-secure accessible": the stock Android kernel drives VFMW from normal world (`libOMX.hisi.video.decoder.so` -> vfmw in the kernel) and the TEE copy exists for secure/DRM paths only [read, assessment doc]. Evidence against: none found. Mitigation: the box has the 150 s SP805 reset net; load with the console attached. The driver also reads `SMMU_INT_STATE_S` (secure) registers; whether a non-secure read of those returns 0 or faults is **[unknown]**.
2. **SMMU / MMU state [inferred].** All kept codecs run with the VDH MMU **bypassed** (`SMMU_CTRL = 0` written on every resume and reset). The vendor stock path *enables* the SMMU (`VDMHAL_V400R003_EnableSmmu`) [read]; the community driver's non-AVS paths use physical addresses and were reported to work on boards that boot through the same AArch32 U-Boot -> kernel handover [read: their comments], but the stock bootloader/firmware on *this* box may leave the MMU enabled with a page table - the bypass write would then change behaviour. Watch for `SMMU state s=... ns=...` lines in the failure print.
3. **Address width [inferred].** DMA mask is 32 bit; RAM is 2 GB at `0x0`; no LPAE. The arm64 tree's `soc` node limits DMA to 1 GiB and says "some masters really cannot reach past 1 GiB"; **our dtsi uses 2 GiB** after a measured GMAC/xHCI failure, and the stock kernel uses the VDH on the MMZ at `0x77C00000-0x7B3FFFFF` (above 1 GiB) [read, assessment doc]. So the VDH is probably fine with high RAM, but that is **not tested**. If probe prints `reserved decoder pool is outside the DMA aperture` or the first frame fails with `-EINVAL`, pin both pools below `0x40000000` (alloc-ranges in the snippet).
4. **CMA size and placement.** Tile/PMV surfaces come from the **default** CMA (the community tree measured that `dma_alloc_noncoherent` bypasses `memory-region`). 64 MiB (today) covers 1080p only barely (about 16 references x 3.2 MiB); 4K needs ~190-200 MiB. The snippet proposes 192 MiB `linux,cma-default` plus an optional 64 MiB non-reusable pool.
5. **HIGHMEM fix is compile-tested only [inferred correct].** `vmap()` of CMA highmem pages + `dma_sync_single_*` by handle. Untested: ARM32 cache maintenance on highmem pages for the CPU alias vs the vmap alias (PIPT D-cache reasoning only). Also `dma_mmap_attrs(..., attrs 0)` for those buffers maps uncached-for-userspace while the kernel alias is cacheable: mismatched attributes on one physical page, the same pattern the community tree used on arm64.
6. **dma-buf export with page-less sg entries.** `histb_vdec_cached_dmabuf_map()` returns an sg table whose entry has `NULL` page and only a DMA address. Importers that call `sg_page()` / iterate pages (some DRM/GEM paths, CPU access through `dma_buf_vmap`) will crash or fail on 32-bit; this was only exercised on arm64 by its authors.
7. **Shared CRG register 0x78.** The clock framework (gates at bits 0/1) and the driver's `regmap` (bits 4-6 resets, [9:8] clock select) both read-modify-write the same register without a common lock. Low risk (the clock gates are enabled in `runtime_resume` before the driver pulses resets) but real.
8. **CABAC blobs**: see section 5. H.264 [read, unvalidated layout]; HEVC [inferred].
9. **6.12 -> 6.18 behavioural drift not visible to the compiler [unknown].** vb2 / m2m / request-API semantics changed between those versions (e.g. job and held-buffer handling). The code compiles clean and I changed nothing but the signatures, but runtime behaviour is untested.
10. **Missing from the port:** AVS/AVS+ (cut), VPSS deinterlace private ioctl is kept (`VIDIOC_HISTB_VPSS_DEI`, uapi header installed) but has no userspace here.
11. **0002 does not apply with `patch`** (section 1).

## 8. Hardware test plan (gated, stop at the first failure)

Setup: serial console attached; `watchdog.handle_boot_enabled=0` net already in place. Stage the kernel image, dtb, `v4l2-mem2mem.ko`, `v4l2-vp9.ko`, `histb-vpss.ko`, `histb-vdec.ko`, the two `.bin` files.

**G0 - clocks only (patch 0009, nodes still disabled).** Boot must be unchanged. `cat /sys/kernel/debug/clk/clk_summary | grep -E 'vpss|vdh|bpd|333m|400m|300m'` should list `vpss_mux` (parent `333m`, 333000000), `clk_vpss`, `clk_vdh`, `clk_vdh_dsp`, `clk_bpd`, all enable_count 0.
**G1 - VPSS probe.** Enable only `&vpss`. `modprobe histb-vpss`. Expect: `histb-vpss f8cb0000.video-post-processing: registered native tile post-processor`. No `/dev` node.
**G2 - VDEC probe.** Enable `&vdec`. `modprobe histb-vdec` (pulls `v4l2-mem2mem`, `videobuf2-*`, `v4l2-vp9`). Expect one line:
`histb-vdec f8c30000.video-codec: registered as /dev/videoN` and `ls /dev/media*`.
Failure map: `-EPROBE_DEFER` -> vpss missing; `failed to get clocks` -> 0009 not in the running kernel or the dtb ids are old; `failed to get CRG syscon` -> crg node lost `syscon`; `reserved decoder pool is outside the DMA aperture` -> see 7.3; a hang/SError right after enabling the node -> see 7.1.
**G3 - capabilities.**
```
v4l2-ctl -d /dev/video0 --info                    # Driver name: histb-vdec, Card type: HiSilicon Hi3798CV200 VDH decoder
v4l2-ctl -d /dev/video0 --list-formats-out        # S264 S265 MG2S VP8F VP9F MPG4 VC1G VC1L   (no AVS)
v4l2-ctl -d /dev/video0 --list-formats            # NV12 (and P010)
v4l2-ctl -d /dev/video0 --list-framesizes=S264    # up to 4096x2304
v4l2-ctl -d /dev/video0 --list-ctrls              # stateless H264/HEVC/MPEG2/VP8/VP9 controls
media-ctl -d /dev/media0 -p
```
**G4 - H.264 1080p to a file (CABAC H.264 table gate).** `ls /lib/firmware/hisilicon/` first.
```
gst-launch-1.0 -v filesrc location=clip.mp4 ! qtdemux ! h264parse ! v4l2slh264dec ! \
   video/x-raw,format=NV12 ! filesink location=hw.nv12
ffmpeg -i clip.mp4 -pix_fmt nv12 -f rawvideo sw.nv12 && cmp hw.nv12 sw.nv12     # bit-exact is the pass
```
Watch `dmesg -w` for `decode failed: state=...` (the driver prints codec name, state, expected, slice count, and the SMMU state words) and `failed to load hisilicon/histb-h264-cabac.bin`. Then `cat /proc/meminfo | grep -i cma` before/during/after (CMA free pages tell you whether 7.4 is real), and `grep -i video /proc/interrupts` (the vdh interrupt (GIC SPI 95) must increment).
**G5 - HEVC** (`v4l2slh265dec`, 8-bit then Main10 -> P010). A failure here with G4 green points at the regenerated HEVC table (section 5).
**G6 - VP9 (`v4l2slvp9dec`), MPEG-2 (`v4l2slmpeg2dec`), VP8 (`v4l2slvp8dec`).** Then stateful MPEG-4 / VC-1 (`v4l2-ctl --stream-from` with raw ES, or gst `v4l2mpeg4dec` if present).
**G7 - 4K and soak.** Raise CMA per the snippet, decode 3840x2160 H.264, then 10 consecutive runs; check `dmesg` for CMA allocation failures and that `grep -i cma /proc/meminfo` returns to baseline after (a leak there would implicate the highmem helper).
**G8 - module removal.** `modprobe -r histb-vdec histb-vpss`: no warnings, CMA back to baseline.
